Solid plan. It’s clear, opinionated, and avoids the usual “one giant daemon” trap.

Main things I’d watch:

1. **The shared config crate is doing too much.**
   Messaging, retries, CLI flags, message definitions, etc. are all in one place. That’s fine at first, but it may become a bottleneck. Split it later if needed.

2. **“No module depends on another” + “modules find each other by name in manifest” is good**, but make sure the name mapping is really simple and boring. If that becomes clever, you’ll regret it.

3. **The 5s timeout rule is risky for long jobs.**
   You already handle long jobs with job IDs, which is good. Just make sure every long-running call immediately returns a job ID and never blocks on the socket waiting for completion.

4. **Current state on reconnect is a great decision.**
   That solves a lot of event-loss pain. Keep it simple: snapshot + tail, or just full resync if that’s easier.

5. **The “bad input → 3 crashes → refuse X” rule is clever but needs care.**
   Make sure the poison mark is per-module and easy to clear manually. Otherwise one bad file can annoy you later.

6. **Your build order is smart.**
   Three modules first, then freeze the message format. Don’t freeze too early.

7. **The biggest risk isn’t the architecture; it’s scope creep.**
   You already have a good rule: *new thing = new module*. Protect that hard.

Overall: this feels like a plan I’d actually build. The design is conservative in the right places and flexible where it should be.

If I had one blunt suggestion: **build `ava-utils-config` as small as possible first**. Just enough to prove messaging, retries, manifests, and the loop check work. Then add the rest only when a real module needs it.

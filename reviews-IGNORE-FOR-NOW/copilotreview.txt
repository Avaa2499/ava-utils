Overall: I think this is a surprisingly coherent plan for something this ambitious.

The strongest thing about it is that you've actually picked a philosophy and followed it consistently. Most "microservice-on-my-desktop" designs collapse because they gradually add exceptions. Here you've got a few hard rules:

process isolation
socket-only communication
no compile-time module dependencies
manifest-driven wiring
systemd as the orchestration layer

Those rules show up everywhere in the design, which is a good sign.

A few things I'd call out.

What I think is particularly good
1. Treating systemd as the platform

This is probably the best decision in the document.

A lot of projects immediately start writing:

service managers
supervisors
registries
health checking
restart logic
socket activation

You've basically said:

Linux already solved this.

Good.

The socket activation approach especially fits the "independent modules" goal.

2. The library + thin executable split

This is one of the best rules in the whole README:

every module is a library crate plus a tiny runtime wrapper

That tends to age very well.

You'll be able to:

test most logic without async
fuzz logic without async
benchmark logic without async
reuse functionality later

And it prevents Tokio from leaking through everything.

3. Manifests contain module names, code contains message names

This is arguably the most important architectural choice you've made.

Without that rule you would eventually get:

call("file-indexer", ...)


all over the codebase.

Then renaming modules becomes painful.

This separation:

Code  -> message names

Manifest -> module names


is the cleanest part of the design.

4. Current-state replay for topics

Good idea.

A lot of event systems accidentally require:

query current state
then
subscribe


which creates races.

Your rule:

connect → immediately receive current state

removes an entire category of bugs.

5. "No broker"

For a personal machine, I'd agree.

Brokers usually become:

SPOF
memory sink
operational complexity

Unix sockets plus systemd gives most of the benefits at a fraction of the complexity.

Areas I'd worry about
1. The cycle ban is probably too strict

This is the biggest thing I'd challenge.

You've got:

No loops of any kind.

In practice many perfectly sensible systems contain cycles.

Example:

file-indexer
    ↓
thumbnail-generator
    ↓
metadata-indexer
    ↓
file-indexer


That's not inherently bad.

The dangerous thing isn't cycles.

The dangerous thing is:

A waits for B
B waits for A


or event storms.

I suspect after 20+ modules you'll find yourself constantly creating exemptions.

I'd consider banning:

synchronous call cycles

rather than

all graph cycles.
2. The "one shared crate" may become gigantic

ava-utils-config currently owns:

protocol
transport
messages
CLI parsing
config
locations

That's five different concerns.

Today that's convenient.

Three years from now it might be:

ava-utils-config
    30,000 lines


and every message change rebuilds half the workspace.

You may eventually want:

ava-utils-wire
ava-utils-messages
ava-utils-cli
ava-utils-paths


even if they're still always used together.

3. MessagePack with field names in every message

This gives excellent compatibility.

But I'd test the cost before committing.

You currently have:

message
 ├─ field names
 └─ values


for every transmission.

For indexing and file watching this is probably fine.

For high-frequency traffic it may become surprisingly chatty.

Not saying it's wrong.

Just benchmark before freezing it.

4. "Producer sends current state"

This needs a very precise definition.

For something like:

files-changed


what is "current state"?

Possibilities:

list of every file known
change journal
generation number
snapshot

The rule is excellent, but I think you'll eventually need explicit snapshot semantics in the protocol.

Otherwise each producer invents its own interpretation.

5. File watcher → current state may explode

Imagine:

2 million files


Subscriber reconnects.

Does the watcher resend all 2 million entries?

Or only current roots?

Or current generation?

I'd design replay semantics early because it affects protocol design.

One thing I think is missing
Message versioning

You currently rely on:

unknown boxes are ignored

which is great.

But eventually you'll need to distinguish:

field absent


from

field intentionally empty


and

field removed in v2


I'd probably put a protocol/message version into the envelope from day one.

Not because you need it now.

Because adding it later is awkward.

One thing I'd simplify

The forced "every module gets run-command" idea.

I'm not convinced that's buying much.

The cleaner architecture is:

CLI
    -> specific calls


instead of:

CLI
    -> run-command
         -> parse argv


Right now you're effectively tunnelling CLI syntax over RPC.

That's elegant for generic dispatch, but it means modules parse command lines despite not being command-line programs.

I suspect you'll revisit this after the first few modules.

What I would build first

I like your initial trio:

file-watcher
file-indexer
file-searcher


because they exercise almost every architectural decision:

events
calls
long jobs
state
reconnection
socket activation
persistence
manifests

If those three work cleanly, the architecture is probably viable.

If those three feel awkward, you'll discover it early before you've built ten more modules.

My biggest prediction

I don't think the architecture will fail because of IPC, systemd, Rust, manifests, or process isolation.

I think the thing most likely to become painful is message ownership.

For example:

search
index-lookup
files-changed
job-progress


are easy.

But after 30 modules you'll start asking:

who owns this message?
who is allowed to emit it?
can multiple modules answer it?
what happens if ownership moves?

I'd be tempted to add one more rule now:

Every message type has exactly one owning module family responsible for its definition and semantics.

That sounds boring, but it prevents protocol drift later.

In short: the design is much stronger than the average "modular utility suite" proposal. The systemd/socket-activation foundation, process isolation, manifest-based wiring, and library/runtime split are all solid choices. The areas I'd stress-test before writing code are the absolute cycle ban, replay semantics for topics, and the long-term growth of ava-utils-config. Those are the parts I can most easily imagine needing redesign after the first dozen modules.

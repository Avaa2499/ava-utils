### What Works Exceptionally Well

1. **Leveraging Native Linux & Systemd:**
Using Unix sockets, systemd socket activation (`LISTEN_FDS`), and modern systemd fault-containment directives (`Restart=always`, `WatchdogSec=`, `MemoryMax=`) gives you a bulletproof process boundary without writing custom daemon supervisors.
2. **Compile-Time Decoupling via Manifests:**
Stitching modules together via manifests (`file-lookup` $\rightarrow$ `file-indexer`) while keeping module names entirely out of the Rust source code is brilliant. It means you can refactor, split, or rename modules with a simple manifest update and a find-and-replace, requiring zero Rust code changes.
3. **The State-Sync-on-Connect Pattern:**
Having producers immediately push their current state upon subscription eliminates an entire class of complex resync handshakes and race conditions.
4. **Tooling Choices:**
`mold` (lightning-fast linking), `sccache` (distributed/local compilation caching), Cargo workspaces, and a single `justfile` provide an elite developer experience for a Rust monorepo.

### Edge Cases and Points to Consider Before Coding

As you start writing `ava-utils-config` and your first modules, keep these architectural nuances in mind:

#### 1. Initial State Sync Size and Memory

* **The Scenario:** Under *“Producers never block... When a subscriber connects, the producer immediately sends the topic's current state.”*
* **The Consideration:** If `file-indexer` has indexed 500,000 files, serializing that entire state into a single MessagePack payload and pushing it over a Unix socket upon reconnection could cause a sudden memory spike or hit socket buffer limits.
* **The Mitigation:** Consider whether initial states can be paginated, streamed as an iterator of chunks, or if you only send a lightweight snapshot/delta sync (e.g., a state version ID followed by recent changes).

#### 2. File Descriptor Passing (`SCM_RIGHTS`)

* **The Scenario:** Rule #1 under "Rules for every module" states: *"Pass references (paths), never bulk bytes over a socket. Handing over file handles gets built when a module first needs it."*
* **The Consideration:** Since you are exclusively on Unix sockets and Linux, you can pass actual file descriptors across processes using ancillary data (`SCM_RIGHTS` via crates like `nix` or `rustix`). When `video-playback` or `compression` needs to read a file indexed by `file-indexer`, being able to transfer an open `OwnedFd` directly avoids repetitive path lookups, permission checks, and race conditions if the file is moved or deleted mid-operation.

#### 3. Monolithic `ava-utils-config` Recompilation

* **The Scenario:** `ava-utils-config` holds every message definition, box name, wiring logic, and flag reader for the entire suite.
* **The Consideration:** In a large suite with dozens of modules, *every* change to a single message in `ava-utils-config` will force a recompilation of `ava-utils-config` and every module that depends on it. While `sccache` and `mold` mitigate this heavily, you may eventually want to segment `ava-utils-config` into domain-specific sub-crates (e.g., `ava-utils-config-media`, `ava-utils-config-fs`) if compile times start creeping up as the project scales.

#### 4. Poison Pill Persistence Safety

* **The Scenario:** Under fault containment: *"Before handling X, a module writes 'working on X' to disk. 3 crashes on the same X $\rightarrow$ X is refused from then on."*
* **The Consideration:** Ensure your persistence logic in `~/.local/state/ava-utils/<module>/` handles corrupted or partially written crash-tracking state gracefully. If a power outage or `kill -9` corrupts the JSON/MessagePack tracking file, a module shouldn't permanently lock itself out of valid operations on startup.

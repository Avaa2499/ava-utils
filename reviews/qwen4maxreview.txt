Strong bones, and the systemd work is the best part — you actually spiked `kill -9`, `abort()`, and connect-during-restart rather than assuming. Most plans at this stage assert that behaviour and get surprised later. The traps section is also genuinely earned knowledge, not decoration.

But there's one claim in here that doesn't hold, and two rules that will start fighting you around module #4. I'd resolve those before writing `ava-utils-config`, because they're the expensive ones to unwind.

## The decoupling story is the weak point

You claim both of these:

- "Renaming or removing a box… the compiler shows every module using it, you fix them, and they're reinstalled together."
- "Each message carries its box names… so updating one module never breaks the others."

Those are different systems. The first is lockstep compile-time coupling; the second is wire-level independence. You've built the first and are describing the benefits of the second.

Centralising every message in `ava-utils-config` doesn't remove coupling, it reshapes it from a mesh into a star. Every module compile-depends on every other module's schemas. At three modules that's invisible. At thirty, adding one optional box to `files-changed` rebuilds and reinstalls audio playback, video playback, compression, and the GUI — none of which care. "The suite is designed to grow indefinitely" and "one crate holds all messages" pull in opposite directions, and the growth is what makes it hurt.

Note also that the self-describing wire format is currently paying cost for a benefit you've decided not to use. If schema changes are always lockstep, field names on every message are overhead for tolerance you never exercise. And `ava-utils-config` is doing five unrelated jobs: transport, framing, retry policy, the entire schema registry, file locations, and flag parsing. That's a god crate by any measure, and "it never runs on its own, so it can't go down" answers a question nobody asked — it's not a runtime SPOF, it's a *change* SPOF.

To be fair, centralisation buys you something real: exhaustive compiler-checked refactors. That's a legitimate trade. The problem is the doc claims independence as well. Pick one consciously. If you want to keep most of both, the cheap move is: `config` stays transport + envelope + manifest + flags, and schemas live in small per-domain crates owned by the producer (`ava-utils-schema-files`, etc.). Consumers depend on the schema crate, never the module. Changing `files-changed` then rebuilds watcher/indexer/GUI, not the whole suite, and "no module depends on another module" stays literally true.

## The cycle ban will break on your first GUI

Trace it: GUI calls `watch-set-roots` on file-watcher. Watcher emits `files-changed` to indexer. Indexer emits `index-changed` to GUI (you've already flagged that topic as "add it when something listens" — the GUI is that something). That's gui → watcher → indexer → gui. Three-module loop, always banned, no exception available.

The workaround is that the GUI never configures the watcher and polls the indexer for status instead. Which is a worse design, chosen to satisfy a linter. You already did this once: the indexer can't tell the watcher what to index, so you inverted ownership of the root list and had the CLI set it. That's the rule driving the architecture rather than the reverse.

And the rule isn't buying the safety you think. You say it yourself: "An allowed loop still has the 5s reply cutoff, so two modules waiting on each other get cut off instead of freezing forever." The deadline is the safety mechanism. A three-cycle with deadlines is no more dangerous than a two-cycle with deadlines, so the 2-only restriction is arbitrary. Event cycles in particular are usually harmless — pub/sub reactivity is a normal pattern, not a defect.

I'd ban *synchronous call* cycles, allow event cycles freely, and rely on per-call deadlines plus a hop counter in the envelope for the rest. Keep the install-time check, just point it at the thing that actually deadlocks.

Also: cycle-freedom is a global property, so installing module D can fail because of a loop among A, B, C. Install has to read every manifest, and unrelated modules can block each other. That's more coupling than "small, independent modules" suggests.

## "Current state on connect" is a much bigger commitment than it looks

This one line silently dictates your entire event model: every topic must have a serialisable current state that fully substitutes for all missed events. That works for state-shaped topics (file lists, playback status). It cannot work for event-shaped ones — "file deleted", "job finished", "key pressed". You can't reconstruct a deletion from a snapshot unless every consumer keeps a full mirror and diffs it.

Concrete consequence: file-watcher must hold a complete snapshot of everything under its roots to serve state-on-connect. So the watcher maintains a file tree and the indexer maintains a file tree. That's two indexes, which violates "never two modules doing the same thing."

Second consequence: overflow → disconnect → reconnect → full resend is a livelock for a slow subscriber. Connect, receive 50k paths, fall behind, overflow, disconnect, reconnect, receive 50k paths. It never catches up. You need a cursor or generation number so a reconnecting subscriber can say "I have epoch 7, send me the delta" — and epochs also let consumers discard stale state arriving after in-flight events. Right now there's no ordering or duplicate-suppression story at all, and state-on-connect plus in-flight events guarantees both.

Decide explicitly which topics are state topics and which are event topics. They need different recovery, and pretending they're the same is where this will hurt.

## The watcher doesn't watch

"A module that only listens (e.g. the indexer) starts when something calls it, or when you start it by hand." Combined with "nothing starts at login," after a fresh login nothing is watching and nothing is indexed until someone happens to run a command. The file watcher is not a file watcher; it's a thing that watches if you remember to poke it.

The distinction you're missing is **listeners must be resident, responders can be on-demand.** Anything subscribing to a topic has to be running for the mesh to function at rest. That's a small set (indexer, maybe a notification sink) and it's fine to enable those sockets at login — it doesn't reintroduce a SPOF.

Related: "once started, a module keeps running until you log out" means every one-off `au` invocation leaves a resident daemon behind. Socket activation gives you idle-exit almost for free, and it also fixes the case where a module that fails on startup restarts every five minutes forever with zero clients. `Restart=always` with no circuit breaker plus `TriggerLimitBurst=0` is an unbounded spin.

## Smaller things that are still real

- **5s vs per-call deadlines.** "No reply within 5s = that module is down" contradicts "every call has a deadline," and it's the wrong inference — slow isn't down. Treating a cold-index lookup as death drops you into 5-minute retry windows and manufactures cascading unavailability under load.
- **Watchdog × poison counter.** `WatchdogSec` kills a module whose library call blocks too long. That looks like a crash on input X. Three strikes and a perfectly valid large file is permanently refused. Also, "libraries stay plain Rust, tokio only in the binary" means the heartbeat has to keep ticking while a plain-Rust library blocks — plan `spawn_blocking` plus an independent heartbeat now, not later.
- **"Refused from then on" needs an expiry.** A half-written file is corrupt once, not forever. Key the blacklist on path + mtime + size, or give it a TTL. And "working on X" must be a set with atomic cleanup, not a single value, or concurrent jobs blame each other.
- **Path lifetimes.** "Pass references, never bulk bytes" plus "module deletes its cache when the job finishes" means A can unlink a file B is still reading. `SCM_RIGHTS` fd passing solves this and shouldn't be deferred — it's the natural primitive for your own rule. Also, your 50k-path batch *is* bulk bytes; the rule needs a max frame size and a chunking story regardless.
- **`run-command` is a confused-deputy surface.** Every module exposes its full argv surface to every other module. I'd make it reachable only from `au`, not module-to-module.
- **systemd floor.** `RestartSteps`/`RestartMaxDelaySec` need 254+. You verified 259, which is fine for your machine, but state the minimum explicitly — RHEL 9 and Ubuntu 22.04 are excluded, and that's a real constraint on "Linux for now."
- **Missing:** envelope version handshake, max message size, where the idempotency table lives and whether it survives restart, and any way to inspect the live mesh. `au status` / `au graph` showing connections and queue depths will save you more debugging time than almost anything else on the list.
- **Help drift.** Manifest carries command names + one-line help; actual flags live in module code. Those will diverge, and flag completion won't work without schemas in the manifest.

## Workflow

"Push after every commit" plus parallel agents plus "rebase and push again" is a rebase storm — N agents contending on `main` means constant rejections and constant rebases over each other. Let agents push to their own branches and serialise merges. Add CI on `main` before you have five agents writing to it.

sccache across worktrees: absolute paths in debug info will tank your hit rate. Set `-C debuginfo=0` for agent builds or use `--remap-path-prefix`.

And I'd not use Haiku for `ava-utils-config`. Framing, partial reads, backpressure, and retry are exactly where subtle bugs are expensive and where a cheap model produces plausible-looking code that fails under load. Haiku for leaf modules and test scaffolding is a good fit.

## Build order

Pick the *hardest* first module, not one chosen after the architecture is finished. Video playback stresses everything you've deferred: realtime, fd passing, bulk data, long jobs, cancel semantics, GUI control, C codec crashes. If the architecture can't carry it, you want to know at step 3, not step 30. Your "~a weekend" for config + manifest + cycle check + CLI with heavy tests including crash tests is optimistic by several times — that's the load-bearing component of the whole suite.

The library/binary split with tokio confined to the binary is the right call and will pay off constantly. Same for process-per-module with the explicit rejection of `catch_unwind`, and for deferring the format freeze until three modules exist. Those instincts are sound. It's the coupling claim and the two absolutist rules I'd fix before pouring concrete.
